AjoBI — Full Development Documentation



Overview

AjoBI has four core features: Auth & AjoScore, Digital Ajo Groups, Savings Goals, and Simple Escrow. The backend is PHP (REST API), the frontend is React. Each developer owns a vertical — one person can work on Ajo Groups while another works on Savings Goals without touching the same files or endpoints.

Feature 2 — Digital Ajo Groups

What it does

Users create or join a savings group. Everyone authorizes Paystack Direct Debit. Every cycle the platform auto-charges all members and auto-disburses the pot to whoever is next in rotation.

Frontend pages

/groups — list of groups user belongs to

/groups/create — form to create a new group

/groups/join/:code — join via invite code

/groups/:id — group dashboard: members, payment status, rotation order, next payout

/groups/:id/setup-debit — Paystack Direct Debit authorization page

Frontend API calls

POST /api/groups/create

POST /api/groups/join

GET  /api/groups/mine

GET  /api/groups/:id

GET  /api/groups/:id/members

GET  /api/groups/:id/payments

POST /api/groups/:id/setup-debit   ← initiates Paystack auth



Backend endpoints

POST /api/groups/create

  - Creates group record

  - Generates unique invite code

  - Adds creator as first member

  - Returns group details + invite link



POST /api/groups/join

  - Validates invite code

  - Checks group is not full

  - Adds user as member

  - Assigns rotation position

  - Returns group details



GET /api/groups/:id

  - Returns group info, member list,

    current cycle, rotation order,

    who has paid, who receives next payout



POST /api/groups/:id/setup-debit

  - Calls Paystack to initialize mandate

  - Returns authorization URL

  - Frontend redirects user to Paystack page

  - After auth, Paystack redirects back with mandate code

  - Backend saves mandate code against member record



[CRON JOB — runs on due date]

  - For each active group where today = collection date:

    - Loop through all members

    - Call Paystack Charge Authorization on each mandate

    - Mark payment as pending



[WEBHOOK — charge.success]

  - Find the group and member from metadata

  - Mark member as paid for this cycle

  - If ALL members paid:

    → Find next recipient in rotation

    → Call Paystack Transfer to their account

    → Mark cycle as complete

    → Update everyone's AjoScore (+2)

    → Move rotation to next person

    → Set next cycle date



[WEBHOOK — charge.failed]

  - Mark member as failed

  - Send reminder notification

  - Update AjoScore (-5 if still unpaid after grace period)



Paystack endpoints this feature uses

POST https://api.paystack.co/subscription     ← set up recurring mandate

POST https://api.paystack.co/charge           ← charge a mandate

POST https://api.paystack.co/transfer         ← disburse to recipient

GET  https://api.paystack.co/transfer/:id     ← verify transfer

Feature 3 — Savings Goals

What it does

User creates a personal savings goal (rent, tax, travel, anything), sets a target amount and deadline. Platform calculates the instalment, auto-debits on schedule via Paystack, and locks the funds until the goal date.

Frontend pages

/savings — list of user's active goals with progress bars

/savings/create — form: goal name, target amount, deadline, frequency

/savings/:id — goal detail: amount saved, next debit, projected completion, break option

Frontend API calls

POST /api/savings/create

GET  /api/savings/mine

GET  /api/savings/:id

POST /api/savings/:id/break   ← early withdrawal

POST /api/savings/:id/setup-debit



Backend endpoints

POST /api/savings/create

  - Receives goal name, target, deadline, frequency

  - Calculates instalment = target ÷ number of periods

  - Creates goal record with status "pending_debit_setup"

  - Returns instalment breakdown



POST /api/savings/:id/setup-debit

  - Initializes Paystack mandate for this goal

  - Returns Paystack authorization URL

  - After auth, saves mandate code

  - Updates goal status to "active"



[CRON JOB — runs on each instalment date]

  - For each active goal where today = next_debit_date:

    - Call Paystack Charge on mandate

    - Mark instalment as pending



[WEBHOOK — charge.success]

  - Add amount to goal's locked_balance

  - Record instalment as paid

  - Check if goal is 100% complete

  - If complete: notify user, unlock for withdrawal

  - Update next_debit_date



POST /api/savings/:id/break

  - Marks goal as broken

  - Releases locked_balance for withdrawal

  - Applies AjoScore penalty (-3)

  - Cancels Paystack mandate



GET /api/savings/:id

  - Returns goal details, progress percentage,

    instalment history, next debit date,

    projected completion date



Database tables

savings_goals

  id, user_id, name, target_amount,

  locked_balance, frequency, deadline,

  instalment_amount, next_debit_date,

  paystack_mandate_code, status

  (pending_debit_setup/active/completed/broken),

  created_at



savings_instalments

  id, goal_id, user_id, amount,

  status (pending/paid/failed),

  paystack_reference, paid_at





Feature 4 — Simple Escrow

What it does

User A creates an escrow request, gets a payment link, shares it. User B pays via that link. Both parties confirm. Funds release automatically. No marketplace. No job matching. Just a link and two confirm buttons.

Frontend pages

/escrow — list of user's escrow requests (created and received)

/escrow/create — form: amount, description, recipient phone/email (optional)

/escrow/:id — status page with confirm button

/pay/esc_:code — public page where User B pays (no login required)

Frontend API calls

POST /api/escrow/create

GET  /api/escrow/mine

GET  /api/escrow/:id

POST /api/escrow/:id/confirm    ← each party calls this

GET  /api/escrow/public/:code   ← public status, no auth needed



Backend endpoints

POST /api/escrow/create

  - Receives amount, description, optional recipient info

  - Creates escrow record with status "awaiting_payment"

  - Calls Paystack Payment Page API to generate payment link

  - Returns link: pay.ajobi.app/esc_xyz123



GET /api/escrow/public/:code

  - No auth required

  - Returns escrow amount, description, status

  - Frontend shows pay button or status message



[WEBHOOK — charge.success from escrow payment link]

  - Matches payment to escrow record via metadata

  - Updates status to "funded"

  - Notifies both parties



POST /api/escrow/:id/confirm

  - Records which party confirmed

  - If both confirmed:

    → Call Paystack Transfer to recipient

    → Update status to "released"

    → Update both users' AjoScores (+1 each)

  - If only one confirmed:

    → Status stays "awaiting_confirmation"



[ADMIN ONLY — dispute handling]

POST /api/admin/escrow/:id/release   ← force release

POST /api/admin/escrow/:id/refund    ← force refund



Paystack endpoints this feature uses

POST https://api.paystack.co/page          ← generate payment link

POST https://api.paystack.co/transfer      ← release funds

POST https://api.paystack.co/refund        ← refund on dispute



Database tables

escrows

  id, creator_user_id, recipient_user_id (nullable),

  amount, description, payment_code,

  paystack_page_id, paystack_reference,

  creator_confirmed (bool), recipient_confirmed (bool),

  status (awaiting_payment/funded/

          awaiting_confirmation/released/

          disputed/refunded),

  created_at, released_at

Backend

All admin endpoints check for role = admin on the JWT before executing. No admin logic is mixed into feature endpoints.



Webhooks — Central Handler

All Paystack webhooks hit one endpoint: POST /api/webhooks/paystack

The handler reads the event field and routes internally:

charge.success     → routes to groups, savings, or escrow

                     based on metadata.source field

transfer.success   → confirms disbursement completed

transfer.failed    → flags for admin review

charge.failed      → updates payment record, triggers notification



Every webhook verifies the Paystack signature header before processing. This is one file, owned by whoever sets up the backend infrastructure.



Shared Rules Across the Whole Team

Authentication — every protected endpoint checks Authorization: Bearer <token> header. The middleware file is written once by Developer 1 and imported everywhere.

AjoScore updates — no feature directly writes to the ajo_score column. Every feature calls a shared updateScore(userId, delta, reason) function. One function, one place to change.

Paystack calls — no feature calls Paystack directly from scattered files. All Paystack logic lives in services/PaystackService.php. Developers call the service, not the raw API.

Error responses — all endpoints return the same shape:

{ "status": false, "message": "What went wrong", "data": null }

{ "status": true, "message": "Success", "data": { ... } }



Environment variables — no API keys in code. Everything in .env:

PAYSTACK_SECRET_KEY=

GEMINI_API_KEY=

JWT_SECRET=

DB_HOST=

DB_NAME=

DB_USER=

DB_PASS=
